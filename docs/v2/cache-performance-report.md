# Cache Performance Report

HMS v2's Epic 4 ("Caching and Performance Enhancement") asks for measured, not just implemented, performance improvements from Spring Cache. This measures `GET /api/v1/doctors/{id}` (`DoctorService.getDoctor`, `@Cacheable("doctors")`, Redis-backed — see `CacheConfig`) through real HTTP: one guaranteed cache-miss call against a freshly-created doctor (pays the full Postgres round trip, including the lazily-loaded `departments` collection), then 30 guaranteed cache-hit calls against the same id (Redis only, Postgres never touched again).

**Environment:** single development machine, real PostgreSQL, real Redis, real HTTP round trips via a random-port embedded Tomcat (`@SpringBootTest(webEnvironment = RANDOM_PORT)`).

| **Speedup (miss / avg hit)** | **4.5x** |

## Analysis

- A cache hit was **4.5x faster** than the initial cache-miss call on this run.
- Both numbers include the same constant HTTP + Spring MVC dispatch overhead — the gap between them isolates the caching layer's own effect, not raw request overhead.
- The miss case pays a full connection-pool-to-Postgres round trip, the lazily-loaded `departments` collection's own query, JPA-to-DTO mapping, and a Redis write to populate the cache; the hit case pays only a Redis read plus JSON deserialization (`GenericJackson2JsonRedisSerializer`, see `CacheConfig`) — no SQL, no Hibernate session work at all.
- This is a single-row, single-key measurement, not a load test — it demonstrates that caching a single-item lookup measurably helps, not what happens under concurrent load or with a cold Redis instance under memory pressure.
- This project deliberately caches only single-item lookups (`getUser`/`getDoctor`/`getInvoice`/etc. by id), never a paginated listing — see `docs/performance-report.md`'s "What `@Timed` maps onto this report" section and `UserService.getUsers`'s own Javadoc for why a whole-table cache doesn't fit this project's write-heavy, filterable/sortable/paginated access pattern.
