Analysis

  • REST was faster (lower avg latency) in 8 of 8 operations measured.
  • Across all operations, REST averaged 17.81 ms and GraphQL averaged 36.21 ms per request.
  • Both styles call the exact same service-layer method for a given operation (e.g. both GET /api/v1/roles/{id} and query { role(...) } call RoleService.getRole), so the gap measured here is transport/protocol overhead — GraphQL's per-request query parsing, validation, and field-by-field resolution — not database or business-logic cost.
  • Biggest gap: Get Role by id — REST ~14 ms vs. GraphQL ~104 ms. Both call the identical RoleService.getRole, so effectively all of that ~90 ms difference is GraphQL's own request-parsing/validation/resolution overhead on that particular query shape, not anything database-side.

Where REST does better

  • Every operation measured here. On this benchmark's fixed, well-known request shapes, REST's simpler request/response cycle (no query string to parse, validate, or resolve field-by-field) was faster in 8 of 8 cases, sometimes dramatically (Get Role by id: REST ~86% faster).
  • Any single-shape, high-throughput endpoint a frontend calls the same way every time — REST's lower per-request overhead compounds at scale.
  • Writes, mutations with side effects, and anything needing standard HTTP semantics (status codes, caching headers, idempotency via verbs) that this benchmark didn't measure directly but that REST still handles more directly than GraphQL's uniform 200-status-plus-body model.

Where GraphQL does better

  • Not raw per-request speed on a fixed shape — this benchmark shows GraphQL losing that comparison every time. Its real advantage is shape, not speed.
  • A caller that needs a different subset of fields/nesting depth per screen (e.g. a mobile client wanting a lean doctor { firstName lastName } vs. an admin dashboard wanting the full departments { name location } tree) — one flexible endpoint instead of several REST DTO variants or bespoke query params.
  • Deeply relational reads where REST would otherwise need several round trips or a heavily pre-flattened DTO (e.g. an appointment's patient and doctor and their departments in one request) — GraphQL resolves the whole shape in a single call, trading some per-request overhead for fewer round trips overall.
  • Consumers who benefit from a strongly-typed, self-documenting schema with introspection (GraphiQL/Altair) over hand-maintained REST API docs.

Both styles call the same service layer in this codebase — see CLAUDE.md's "one service layer, multiple front doors" principle. Re-run RestVsGraphQlBenchmarkTest (disabled by default — see its Javadoc) to regenerate these numbers.
