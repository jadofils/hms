CSRF Token Mechanism — Demo

Illustrates Spring Security's CSRF protection on a single, deliberately-isolated form endpoint (HMS v4, Epic 3.1). This is the only path in the app where it's turned on — everywhere else is a stateless, bearer-JWT REST/GraphQL API, which authenticates via an Authorization header a browser never attaches automatically, so there's nothing for CSRF to exploit there in the first place. See CsrfDemoSecurityConfig's Javadoc for the full reasoning.

The token behind these forms

Generated by Spring Security's CsrfFilter for this session and exposed as the CsrfToken request attribute — read directly by CsrfDemoController, not stored or generated by this app itself.

parameter name: _csrf
header name: X-CSRF-TOKEN
token: token-value

Try both forms

Both POST to this exact same /docs/csrf-demo endpoint. Only the difference between them is the hidden token field.

Form A — carries the real token

Hidden field auto-injected by Thymeleaf's CsrfRequestDataValueProcessor integration on any th:action form — matches the token box above.

Expected: 200 — reaches the controller, banner above appears.

Form B — token deliberately omitted

Stands in for a forged cross-site submission with no way to know the token.

Expected: 403 Forbidden — CsrfFilter rejects it before the controller ever runs.

Every other endpoint in this app disables CSRF entirely — see SecurityConfig's .csrf(csrf -> csrf.disable()) and its own Javadoc for why that's correct for a bearer-JWT API, not an oversight.
